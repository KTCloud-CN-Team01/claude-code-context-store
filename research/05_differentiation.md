# 0번 과제 — 차별화 전략 (Value Proposition Canvas)

> 인풋: [04_pain_points.md](./04_pain_points.md)
> 고객 정의: 본 프로젝트는 상용 서비스가 아닌 KT Tech Up 실무 과제(결제·콘텐츠 도메인 MSA 구축)이므로, Value Proposition Canvas의 "고객"은 **"결제·콘텐츠 e-Commerce 플랫폼을 클라우드 네이티브로 운영해야 하는 SRE/플랫폼 엔지니어링 팀"** 페르소나로 설정. 우리 팀 스스로가 1차 고객이며, 동일 입장의 실무 팀 일반에게도 적용 가능한 결론을 목표로 함.

---

## 1. Customer Profile (고객 프로파일)

### 1-1. Customer Jobs (해야 하는 일)
- **기능적 Job**: 결제 트랜잭션의 일관성을 보장하면서 장애 시에도 서비스 가용성을 유지해야 함 / 신규 기능을 빠르게 배포하면서도 결제 도메인 특성상 무중단·안전성을 동시에 만족시켜야 함 / 서비스 메시·카오스 엔지니어링 같은 신기술 도입 여부를 제한된 시간 안에 합리적으로 판단해야 함.
- **사회적 Job**: 장애 발생 시 투명하게 공유해 조직 내 신뢰와 학습 문화를 구축해야 함(블레임리스 포스트모템).
- **감정적 Job**: "장애가 났을 때 원인을 빠르게 알 수 있다"는 확신, "이 아키텍처 결정이 근거 있는 선택이었다"는 확신이 필요함.

### 1-2. Pains ([04_pain_points.md](./04_pain_points.md)에서 직접 매핑)
| Pain | 출처 페인포인트 |
|---|---|
| 서비스 메시를 "도입해야 하나 말아야 하나" 판단할 정량 근거가 없음 | PP-1 |
| 결제 네트워크 예외의 Unknown 상태가 자동으로 처리되지 않고 사람이 개입해야 함 | PP-2 |
| 카오스 실험을 했는지/안 했는지조차 사내·사외에 기록이 안 남음 | PP-3 |
| 장애가 나도 회고가 공유되지 않아 같은 실수가 반복됨 | PP-4 |
| 레거시와 신규 인프라가 오래 공존하며 임시 연결 솔루션이 영구화됨 | PP-5 |
| "MSA로 잘게 쪼개는 것"이 항상 정답인지 의심 없이 진행하다 복잡도만 증가 | PP-6 |

### 1-3. Gains (얻고 싶은 것)
- 메시·복원력 라이브러리 도입 여부를 **숫자(CPU 오버헤드, 레이턴시, 자동 복구율)**로 설명할 수 있는 것.
- 장애 주입 → 자동 복구 → 회고 공개까지 **하나의 재현 가능한 파이프라인**으로 묶여 있는 것.
- 서비스 경계가 "도메인 경계"를 그대로 반영해 불필요한 분산 복잡도가 없는 것.

## 2. Value Map (가치 제안)

### 2-1. Products & Services (우리 프로젝트의 산출물)
- DDD Bounded Context 기반 3~5개 서비스로 분리한 결제·콘텐츠 MSA (1단계)
- Istio 등 서비스 메시 1종 설치 + mTLS + 카나리 라우팅 (2단계)
- 서킷 브레이커/재시도/타임아웃 정책 + 카오스 실험 + 통합 케이스 스터디 (3단계)

### 2-2. Pain Relievers (페인 해소 방법)
| Pain Reliever | 해소하는 Pain |
|---|---|
| 메시 도입 전/후 CPU·레이턴시·에러율을 **직접 측정해 도입 근거 데이터화**(Shopify 사례를 벤치마크 삼아 우리 환경에 재현) | PP-1 |
| Saga 패턴 + 명시적 서킷 브레이커(Resilience4j)로 결제 Unknown 상태의 **자동 보상 처리율을 정량 측정** | PP-2 |
| 3단계 카오스 실험을 **사전 설계 → 실시 → 결과 공개**까지 하나의 산출물로 의무화 | PP-3 |
| Blameless Postmortem 템플릿을 프로젝트 표준 문서로 채택, 모든 장애·실험 결과를 케이스 스터디에 포함 | PP-4 |
| 처음부터 **단일 오케스트레이터·단일 클러스터**로 설계해 하이브리드 과도기 부채를 원천 차단 | PP-5 |
| Bounded Context를 "잘게 쪼개기"가 아닌 **결제 일관성 경계 단위**로 최소화(Shopify·당근페이 반례를 설계 근거로 명문화) | PP-6 |

### 2-3. Gain Creators (게인 창출 방법)
- 서비스 메시 도입 전/후 비교를 **대시보드(RPS/에러율/지연/mTLS)**로 시각화 → "근거 있는 도입 판단" 직접 경험.
- 카오스 실험 → 복구 시간 측정 → 회고 공개의 **전 과정을 1개 문서로 추적 가능**하게 구성 → 재현 가능한 신뢰성 문화 시연.
- 도메인 경계 기반 서비스 분리 근거를 02/04 단계 비교 데이터로 뒷받침 → "왜 이렇게 나눴는지" 설명 가능한 아키텍처.

## 3. Fit 요약 — 우리 프로젝트의 차별화 메시지

> **"6개 선도 기업 중 어느 한 곳도 메시 도입 ROI·카오스 실험 결과·장애 회고를 동시에 투명하게 공개하지 않는다. 우리 프로젝트는 이 세 가지(정량적 메시 도입 근거 + 재현 가능한 카오스 실험 + 블레임리스 포스트모템)를 하나의 파이프라인으로 묶어 산출물화한다는 점에서 차별화된다."**

- Shopify의 정량적 비용 검증 문화(PP-1 해소 방식의 벤치마크)
- 11번가의 OSS 기여형 카오스 엔지니어링(PP-3 해소 방식의 벤치마크)
- 당근마켓의 투명한 장애 회고 문화(PP-4 해소 방식의 벤치마크)

→ 세 회사 각각이 부분적으로만 잘하는 것을 **하나의 프로젝트 안에서 통합 시연**하는 것이 핵심 차별화 포인트.
