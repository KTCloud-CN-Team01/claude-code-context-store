# 04 — 페인포인트 도출 (MECE + 피쉬본 분석)

> 인풋: [02_service_selection.md](./02_service_selection.md), [03_comparison_matrix.md](./03_comparison_matrix.md)
> 방법론: 6개 기업 비교에서 관찰된 격차/리스크를 **MECE(상호배타·전체포괄)** 기준 4개 카테고리로 분류한 뒤, 핵심 질문에 대해 **피쉬본(이시카와) 다이어그램**으로 근본원인을 추적. 모든 근거는 01_company_profiles.md의 실제 출처에서만 인용 — 직접적 출처가 없는 항목은 "정황 기반 추정"으로 명시.

---

## 1. 핵심 질문 (피쉬본 Head/Effect)

> **"왜 결제·콘텐츠 도메인의 클라우드 네이티브 플랫폼은 기업마다 복원력·관찰성 성숙도 격차가 크고, 특히 국내 기업은 그 격차를 외부에서 검증하기 어려운가?"**

## 2. MECE 분류 — 4개 카테고리 (Bone)

| 카테고리 | 정의 | 해당 안 되는 것 |
|---|---|---|
| **A. 기술/아키텍처(Technology)** | 서비스 분리 단위, 메시·복원력 라이브러리 선택 등 설계 레벨 원인 | 조직 운영 방식, 공시 관행 |
| **B. 프로세스/거버넌스(Process)** | 배포·테스트·장애 대응 절차, 카오스 엔지니어링 실시 여부 | 기술 스택 자체 |
| **C. 조직문화/공시(People & Transparency)** | 포스트모템 공개, 학습 문화, 대외 기술 공유 관행 | 인프라 자원 |
| **D. 인프라/환경(Environment)** | 멀티/하이브리드 클라우드 전환 상태, 레거시 잔존 | 애플리케이션 코드 |

4개 카테고리는 서로 겹치지 않고(상호배타), 6개 기업 비교에서 관찰된 모든 격차 요인을 포괄한다(전체포괄).

## 4. 페인포인트 6개 (카테고리별 근본원인 → 구체화)

### PP-1. [A] 서비스 메시 도입의 ROI 판단 근거 부재
- **근본원인**: 서비스 메시는 "표준 관행"으로 알려져 있지만, 실제로는 Envoy 사이드카의 CPU 비용(Shopify가 1M RPS당 월 $5만+로 정량화)과 운영 복잡도 증가가 뒤따름. 그런데도 이를 정량 비교해 "왜 도입/보류했는지" 공개하는 기업은 6개 중 Shopify 1곳뿐.
- **증거**: Shopify는 평가 후 보류, Alibaba/Walmart는 적극 도입, 11번가/카카오페이는 미도입 추정 — 그러나 **어느 쪽도 "왜 그 선택을 했는지"에 대한 비용-편익 데이터를 공개하지 않음**(Shopify 제외).
- **시사점**: 우리 프로젝트는 메시 도입 전/후 리소스 사용량·레이턴시를 직접 측정해 "도입 근거"를 1차 데이터로 만들 수 있는 차별점.

### PP-2. [A] 분산 트랜잭션의 모호 상태(Unknown) 처리가 자동화되지 않음
- **근본원인**: 결제 도메인 특유의 네트워크 예외(타임아웃 등)는 성공/실패로 이분화할 수 없는 "Unknown" 상태를 필연적으로 발생시킴. 카카오페이는 이를 3상태 모델 + tx_key 멱등성으로 처리하지만, 공개 자료상 **PG사 자동 전환·서킷 브레이커 등 자동화된 보상 메커니즘은 확인되지 않고, 수기 처리 가능성이 시사됨**.
- **증거**: [MSA 환경 네트워크 예외 처리](https://tech.kakaopay.com/post/msa-transaction/)
- **시사점**: Saga 패턴 + 명시적 서킷 브레이커(Resilience4j 등)를 결합해 Unknown 상태의 자동 보상 비율을 정량 측정하는 것이 차별화 포인트가 될 수 있음.

### PP-3. [B] 결제 도메인에서는 카오스 엔지니어링 실시 자체가 보수적
- **근본원인**: 카오스 엔지니어링은 "해야 한다"는 합의는 있지만 결제 도메인처럼 실패 비용이 큰 영역일수록 실제 운영 환경에서의 실시·공개 둘 다 꺼려짐.
- **증거**(2026-06-30 재조사로 갱신): Alibaba(ChaosBlade, CNCF Sandbox)·11번가(Chaos Mesh+ToxiProxy, OSS 컨트리뷰션)·Walmart(Concord+Gremlin, 성숙도 레벨1~3 체계, Chaos Conf 2018 발표)는 모두 명확히 확인됨. **그러나 결제 도메인 본체인 카카오페이만 유일하게 순수 카오스 엔지니어링 공개 자료가 전무**(인접한 DR 훈련은 계열사인 카카오페이증권 단위로만 확인) — 비결제 도메인(이커머스/오픈마켓) 기업들이 더 적극적으로 카오스 엔지니어링을 공개하는 반면, 결제 도메인 기업은 상대적으로 보수적인 패턴이 시사됨.
- **시사점**: 04 단계 이후 우리 프로젝트의 (3)단계(복원력·관찰성)에서 카오스 실험을 "결과 공개"까지 포함해 설계하면, 특히 결제 도메인에서 드문 이 공백을 메우는 차별화가 됨.

### PP-4. [C] 국내 기업의 포스트모템 공개 문화 부재
- **근본원인**: 기술 블로그는 "성공 사례·신규 기능" 위주로 작성되고, 장애·실패 회고는 조직 평판 리스크로 인식되어 공개를 꺼림.
- **증거**: 11번가·카카오페이는 공개 포스트모템이 사실상 없음. **당근마켓만 예외적으로 투명**(Elasticsearch Cold Node 장애 → search-coordinator 워밍업 시스템 구축까지 1인칭 상세 회고 공개).
- **시사점**: Blameless Postmortem 템플릿을 프로젝트 산출물에 포함시키고, (3)단계 카오스 실험 결과를 의도적으로 "실패 사례 공개" 형식으로 정리하면 국내 기업 평균 대비 투명성에서 차별화 가능.

### PP-5. [D] 하이브리드 인프라 과도기의 임시방편이 기술부채로 고착
- **근본원인**: "전면 클라우드 전환"은 선언되지만 실제로는 레거시 IDC와 신규 클라우드가 장기간 공존하며, 이를 잇는 브릿지 솔루션(자체 Operator 등)이 임시방편에서 영구 구성요소로 굳어짐.
- **증거**: 11번가(IDC+EKS 하이브리드, Eurekube Operator로 Eureka↔EKS 서비스 디스커버리 연결), 카카오페이증권(EKS+IDC+Kakao Cloud 3중 클러스터).
- **시사점**: 우리 프로젝트는 처음부터 단일 클러스터·단일 오케스트레이터로 설계해 "과도기 부채"를 원천 차단하는 것 자체를 아키텍처 결정 근거로 문서화 가능.

### PP-6. [A] "MSA = 정답"이라는 전제가 도메인 특성을 무시할 위험
- **근본원인**: 마이크로서비스 분리는 조직 확장성에는 유리하지만, 트랜잭션 일관성이 중요한 도메인(결제)이나 read-heavy 도메인에서는 오히려 분산 트랜잭션·네트워크 홉 증가로 복잡도만 키울 수 있음.
- **증거**: Shopify(모듈러 모놀리스+Pod 샤딩으로 의도적 비-MSA), 당근페이(Hexagonal/Clean Architecture 모노레포로 MSA 대신 점진적 전환) — 둘 다 "분리 안 함"을 데이터 기반으로 정당화한 사례.
- **시사점**: 05_differentiation 단계에서 우리 프로젝트의 Bounded Context 개수를 "최대한 잘게"가 아니라 "결제 일관성 경계 단위"로 최소화하는 근거로 사용.

## 5. MECE 커버리지 체크

| 카테고리 | 페인포인트 |
|---|---|
| A. 기술/아키텍처 | PP-1, PP-2, PP-6 |
| B. 프로세스/거버넌스 | PP-3 |
| C. 조직문화/공시 | PP-4 |
| D. 인프라/환경 | PP-5 |

4개 카테고리 모두 최소 1개 이상의 페인포인트로 커버됨 — 누락 카테고리 없음(MECE 충족). 총 6개로 과제 요구치(5개 이상) 충족.
