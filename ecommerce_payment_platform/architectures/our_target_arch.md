# 우리 프로젝트 목표 아키텍처

> 참조일: 2026-06-30
> 기존 6개사([02_service_selection.md](../report/02_service_selection.md))의 페인포인트(PP-1~PP-6, [04_pain_points.md](../report/04_pain_points.md))를 해소하는 설계.
> 차별화 전략 출처: [05_differentiation.md](../report/05_differentiation.md) — 메시 도입 근거 데이터화(Shopify 벤치마크) + 재현 가능한 카오스 실험(11번가 벤치마크) + 블레임리스 포스트모템(당근마켓 벤치마크)을 **하나의 파이프라인**으로 통합.
> 단계 구분: (1) 도메인·서비스 분리 → (2) 서비스 메시 → (3) 복원력·관찰성·카오스 엔지니어링 (커리큘럼 3단계 그대로 반영, 임의의 "3대 축" 아님).

---

## 1. 전체 아키텍처 — (1)단계: 도메인·서비스 분리

```
┌──────────────────────────────────────────────────────────────────────────┐
│         (1) Bounded Context 기반 서비스 분리 — PP-6 해소                   │
├──────────────────────────────────────────────────────────────────────────┤
│                                                                          │
│  설계 원칙: "잘게 쪼개기"가 아닌 **결제 일관성 경계 단위**로 최소화           │
│  (Shopify 모듈러 모놀리스+Pod 샤딩 / 당근페이 모노레포 반례를 근거로 채택)   │
│                                                                          │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐                                │
│  │ 주문     │ │ 결제     │ │ 상품/콘텐츠│   (3~5개 서비스로 최소화)        │
│  │ Service  │ │ Service  │ │ Service   │                                │
│  └──────────┘ └──────────┘ └──────────┘                                │
│         하나의 트랜잭션 경계(주문→결제→권한부여)는 분리하지 않고             │
│         하나의 Bounded Context로 묶어 분산 트랜잭션 자체를 최소화           │
│                                                                          │
│  [인프라 — 단일 오케스트레이터·단일 클러스터로 시작]                        │
│  (11번가 IDC+EKS, 카카오페이 3중 클러스터의 "하이브리드 과도기 부채"        │
│   사례를 반례로 삼아 처음부터 단일 구성 — PP-5 해소)                       │
│  Kubernetes(EKS) 단일 클러스터 + 네임스페이스 기반 환경 분리               │
│                                                                          │
└──────────────────────────────────────────────────────────────────────────┘
```

## 2. (2)단계: 서비스 메시 — 정량적 도입 근거 데이터화 (PP-1 해소)

```
┌──────────────────────────────────────────────────────────────────────────┐
│  Shopify는 메시 도입을 "평가 후 비용 정량화→보류"까지 공개한 유일한 사례.   │
│  우리 프로젝트는 한 걸음 더 나아가 **도입 전/후를 직접 측정해 비교**한다.    │
├──────────────────────────────────────────────────────────────────────────┤
│                                                                          │
│  [측정 1] 메시 미적용 베이스라인                                          │
│  서비스 간 직접 HTTP 호출, 애플리케이션 레벨 재시도/타임아웃만 적용         │
│         │                                                                │
│         ▼ 동일 부하로 A/B 비교                                            │
│  [측정 2] Istio + Envoy Sidecar 적용                                     │
│  ┌────────────────────────────────────────────────────────────┐          │
│  │ Istio Control Plane                                          │          │
│  │ └── Envoy Sidecar(전 Pod 주입)                                │          │
│  │     ├── mTLS 자동화                                           │          │
│  │     ├── Circuit Breaker(서비스 간)                            │          │
│  │     ├── Retry/Timeout 정책 선언적 관리                        │          │
│  │     └── 카나리 라우팅(트래픽 분할)                             │          │
│  └────────────────────────────────────────────────────────────┘          │
│         │                                                                │
│         ▼                                                                │
│  [비교 대시보드 — "도입 근거"를 데이터로 제시]                             │
│  CPU/메모리 오버헤드(사이드카) │ P50/P99 레이턴시 증감 │ 에러율 변화        │
│  → Shopify의 "1M RPS당 월 $5만+" 정량화 방식을 우리 환경 규모에 재현       │
│                                                                          │
└──────────────────────────────────────────────────────────────────────────┘
```

## 3. (3)단계: 복원력·관찰성·카오스 엔지니어링

```
┌──────────────────────────────────────────────────────────────────────────┐
│  [분산 트랜잭션 Unknown 상태 자동 보상 — PP-2 해소]                        │
│  카카오페이의 3상태 모델(성공/실패/Unknown)에서 한 걸음 더:                 │
│  Saga 패턴 + 명시적 Circuit Breaker(Resilience4j)로 자동 보상 처리율 측정  │
│                                                                          │
│  주문 서비스 → 결제 요청                                                  │
│     ├── 성공 → 권한부여 이벤트 발행                                       │
│     ├── 명시적 실패 → 보상: 주문 취소(자동)                               │
│     └── Unknown(타임아웃) → Resilience4j CB로 재시도 한도 관리             │
│           └── 한도 초과 시 → 보상 트랜잭션 자동 실행(수기 개입 최소화)      │
│                                                                          │
├──────────────────────────────────────────────────────────────────────────┤
│  [카오스 엔지니어링 — 사전설계→실시→결과공개 파이프라인 — PP-3 해소]        │
│  11번가(Chaos Mesh+ToxiProxy→OSS 컨트리뷰션)를 벤치마크로,                 │
│  결제 도메인에서 드문 "결과 공개"까지 의무화                               │
│                                                                          │
│  실험 설계 문서 → Chaos Mesh 장애 주입(Pod kill/지연/네트워크 단절)        │
│       → 자동 복구 시간 측정 → 결과를 Blameless Postmortem으로 공개          │
│                                                                          │
├──────────────────────────────────────────────────────────────────────────┤
│  [관찰성 — LGTM 스택]                                                    │
│  OpenTelemetry Collector → Loki(로그)/Grafana(대시보드)/                  │
│  Tempo(트레이싱)/Prometheus(메트릭) + Alertmanager(SLO 기반 알림)         │
│                                                                          │
├──────────────────────────────────────────────────────────────────────────┤
│  [장애 회고 — 블레임리스 포스트모템 — PP-4 해소]                          │
│  당근마켓(Elasticsearch Cold Node 사례)을 벤치마크로,                     │
│  카오스 실험 결과 + 실제 장애 모두 동일 템플릿으로 공개 문서화             │
│  → 6개사 중 어느 한 곳도 안 하는 "메시 근거+카오스 결과+회고"의 통합 시연   │
└──────────────────────────────────────────────────────────────────────────┘
```

## 4. 페인포인트 해소 매핑

| PP ID | 페인포인트 | 해소 설계 | 벤치마크 기업 |
|---|---|---|---|
| PP-1 | 메시 도입 ROI 판단 근거 부재 | 도입 전/후 A/B 측정 대시보드 | Shopify(정량화 방법론) |
| PP-2 | 분산 트랜잭션 Unknown 상태 수기 처리 | Saga + Resilience4j 자동 보상 | 카카오페이(반례로 보강) |
| PP-3 | 카오스 엔지니어링 결제 도메인 보수성 | 설계→실시→공개 의무화 파이프라인 | 11번가(OSS 컨트리뷰션 사례) |
| PP-4 | 국내 기업 포스트모템 비공개 문화 | 블레임리스 포스트모템 표준 문서화 | 당근마켓(투명 회고 사례) |
| PP-5 | 하이브리드 과도기 기술부채 고착 | 단일 클러스터·단일 오케스트레이터 출발 | 11번가/카카오페이(반례) |
| PP-6 | "MSA=정답" 전제의 도메인 무시 위험 | 결제 일관성 경계 단위로 BC 최소화(3~5개) | Shopify/당근페이(반례) |
