### PP-01: 決済スパイク時のカスケード障害

**概要**

```
セール・キャンペーン時に決済サービスへの集中リクエストが
DB コネクション枯渇 → 決済サービスダウン → 注文サービスもダウン
というカスケード障害を引き起こす。
```

**フィッシュボーン因果分析**

```
                             [決済スパイク時のカスケード障害]
                                          │
          ┌───────────────┬───────────────┼───────────────┬───────────────┐
       [設計]           [容量]          [運用]          [依存]         [監視]
          │               │               │               │               │
  MSA 分割が粗い    HPA 設定不足    負荷試験不十分   PG API レート制限  アラート遅延
  DB 共有（分離なし）コネクション池不足  スパイク想定外  サーキットブレーカーなし  閾値設定誤り
  同期 RPC 連鎖   キャッシュ未使用  キャパプランなし  タイムアウト未設定     ─
```

**実際の障害事例**

| サービス | 日時 | 内容 | ソース |
|---------|------|------|------|
| Market Kurly | 2021 年以降複数回 | 새벽배송 주문 폭주 시 결제 지연 | https://helloworld.kurly.com/blog/database-failover/ |
| Coupang | 2021 로켓배송 이벤트 | 결제 서버 순간 과부하 보고 | SNS・커뮤니티 보고 |
| Inflearn | 할인 이벤트 시 | 결제 응답 지연 (수 십 초) | 사용자 SNS 신고 |

**CN 解決アプローチ**

```
① 決済サービスの DB 分離（Database per Service パターン）
② 非同期決済フロー導入（Saga パターン）
   주문생성 → (MQ) → 결제요청 → (MQ) → 재고차감
③ 決済サービス手前にキューイング（KEDA: Kafka ベース HPA）
④ PG 呼び出しにサーキットブレーカー（Resilience4j）
⑤ カオス実験: 決済 DB 遅延注入テスト
```

### PP-02: MSA 移行期のデータ整合性崩壊

**概要**

```
モノリスから MSA への段階的移行（Strangler Fig Pattern）の過程で、
旧モノリス DB と新マイクロサービス DB の二重書き込みが発生。
結果: 注文情報と決済情報の不一致（二重決済 / 未決済）。
```

**フィッシュボーン因果分析**

```
                        [データ整合性崩壊]
                                │
          ┌─────────────────────┼─────────────────────┐
       [設計]               [移行手順]              [トランザクション]
          │                     │                       │
  Saga パターン未実装   DB 移行ロールバック設計不足    分散トランザクションなし
  共有 DB（境界不明確）  旧新 DB 同期ロジック複雑      2PC 未採用
  イベントソーシング未採用  データ移行テスト不足        補償トランザクション未設計
```

**実際の障害事例**

| サービス | 内容 | ソース |
|---------|------|------|
| Inflearn | 강의 구매 후 수강 목록 미반영（결제 성공 / 권한 부여 실패）| https://tech.inflearn.com/post/276 |
| Market Kurly | 주문 상태와 결제 상태 불일치로 CS 폭증 | https://helloworld.kurly.com/blog/introducing-event-storming/ |
| Coupang（推定）| 초기 MSA 전환 시 주문/결제 DB 분리 과정에서 정합성 이슈 발생 | 추정（공개 정보 기반）|

**CN 解決アプローチ**

```
① Saga パターン（Choreography / Orchestration）採用
   주문서비스 → OrderCreated(이벤트) → 결제서비스 → PaymentCompleted(이벤트)
   → 재고서비스 → StockReserved(이벤트)
   失敗時: 補償トランザクション（CompensatoryTransaction）

② Outbox パターン: DB 書き込みと同時に Outbox テーブルへ記録
   → Debezium（CDC）で Kafka に転送 → 確実な非同期配信

③ Event Sourcing: 状態変化をイベントとして記録
   → 任意時点の状態再現・監査ログ自動生成

参照: https://microservices.io/patterns/data/saga.html
```

### PP-03: オブザーバビリティ欠如による障害検知遅延

**概要**

```
Metrics だけでは障害の根本原因特定に時間がかかる。
特に Traces 欠如により「どのサービス間の呼び出しが遅い/失敗しているか」が
ログを手動で追わないと分からない。
結果: MTTR（平均復旧時間）の長期化。
```

**フィッシュボーン因果分析**

```
                       [障害検知・原因特定遅延]
                                │
          ┌──────────────────────┼──────────────────────┐
       [観測]               [アラート]              [組織]
          │                     │                     │
  Traces 未実装           閾値設定が粗い          On-call 文化なし
  Logs が構造化されていない  誤検知アラートが多い     Runbook 未整備
  メトリクス粒度が粗い     アラート疲れ（無視）      ポストモーテム未実施
```

**実際の事例**

| サービス | 事例 | ソース |
|---------|------|------|
| Market Kurly | 배포 후 에러율 상승을 수 분 후에 감지（알림 지연）| https://helloworld.kurly.com/blog/kurly-devops-transformation/ |
| Inflearn | 결제 오류 유저 신고로 인지（능동 감지 없음）| 사용자 SNS 보고（2022-2023）|
| Netflix（過去）| 2012 年 AWS 장애 시 전체 서비스 다운 → カオスエンジニアリング強化のきっかけ | https://netflixtechblog.com/post-mortem-of-october-22-2012-aws-degradation-efcee3ab40d5 |

**CN 解決アプローチ**

```
① OpenTelemetry 標準化
   → Traces を全マイクロサービスに自動挿入（Auto-instrumentation）

② 構造化ログ（JSON 形式）+ 相関 ID（TraceID 埋め込み）
   → Logs / Traces を相関させてドリルダウン可能に

③ SLO ベースのアラート（エラーバジェット消費率で通知）
   → 誤検知を減らし、本当に重要な障害のみ通知

④ Grafana Tempo + Loki + Prometheus（LGTM スタック）採用
   → オープンソース + ローカルデプロイで低コスト
```

### PP-04: デプロイ時のゼロダウンタイム未達

**概要**

```
Rolling Update / Blue-Green デプロイの設定不備で
デプロイ中に一時的なエラーレート上昇（5xx）が発生。
特に결제 관련 서비스의 경우 デプロイ時間帯にユーザーが決済エラーを体験。
```

**実際の事例**

| サービス | 内容 | ソース |
|---------|------|------|
| Inflearn | 배포 중 일부 유저 504 오류 경험 | 사용자 트위터 보고（복수 사례）|
| Market Kurly | 새벽 배포 중 주문 불가 현상 | https://helloworld.kurly.com/blog/kurly-devops-transformation/ |

**CN 解決アプローチ**

```
① Readiness / Liveness Probe の適切な設定
   → 新 Pod が起動完了するまでトラフィックを送らない

② PodDisruptionBudget（PDB）設定
   → ローリングアップデート中も最小稼働数を保証

③ Canary Deployment + 自動メトリクス検証（Argo Rollouts）
   → 新バージョンを 5% のトラフィックで検証してから拡大

④ 非互換 API の Versioning（v1 / v2 並行稼働）
   → デプロイ中の旧クライアントとの互換性維持
```

### PP-05: サービスメッシュ未整備による障害伝播

**概要**

```
サービスメッシュがない場合、あるマイクロサービスの障害が
呼び出し元サービスにタイムアウトとして伝播し、
スレッドプールの枯渇 → 上位サービスも障害（カスケード）。
```

**実際の事例**

| サービス | 内容 | ソース |
|---------|------|------|
| Netflix（過去）| Hystrix 導入前はカスケード障害が頻発 | https://github.com/Netflix/Hystrix/wiki |
| Coupang（推定）| 결제 PG 타임아웃 → 주문 서비스 스레드 고갈 | 추정（공개 사례 없음）|

**CN 解決アプローチ**

```
① Istio + Envoy によるサービスメッシュ導入
   → 全サービスにサイドカー注入でトラフィック制御

② Circuit Breaker のメッシュレイヤー実装
   → アプリコード変更なしにサーキットブレーカー適用

③ Retry / Timeout をメッシュで一元管理
   → 各サービスの retry ロジック重複排除

④ mTLS の自動化
   → 決済サービス間通信を暗号化（PCI DSS 要件対応）
```

### PP-06: マルチ PG 統合の脆弱性（ベンダー依存）

**概要**

```
単一の PG（Payment Gateway）への依存で、
その PG の障害が自社サービス全体の決済停止に直結する。
韓国では 토스페이먼츠 / KakaoPay / NaverPay が主要 PG だが
いずれも過去に大規模障害を経験している。
```

**実際の障害事例**

| PG | 日時 | 内容 | ソース |
|----|------|------|------|
| 토스페이먼츠 | 2022-05-31 | 전국 결제 장애（약 1시간）| https://blog.toss.im/article/toss-service-incident-postmortem-20220531 |
| KakaoPay | 2022-10-15 | 카카오 데이터센터 화재로 인한 대규모 장애 | https://www.kakaocorp.com/ir/news |
| NaverPay | 2023 복수 사례 | 결제 지연 및 오류 | SNS 사용자 보고 |

**CN 解決アプローチ**

```
① 複数 PG 同時登録 + 障害時の自動フェイルオーバー
   정상: 토스페이먼츠 → 장애감지 → KakaoPay へ自動切替

② PG アダプターパターン（Adapter Pattern）
   → 共通 PaymentPort インターフェースで PG を抽象化
   → PG 変更時もアプリコード修正不要

③ Circuit Breaker per PG
   → PG ごとに独立したサーキットブレーカーで隔離

④ Payment の冪等性（Idempotency）保証
   → 同じ注文 ID の二重課金を防止
   → Idempotency-Key ヘッダー + Redis による重複チェック
```

### PP-07: CDN 設定ミスによるコンテンツ配信障害

**概要**

```
Inflearn のような動画 + テキストコンテンツを混在するサービスでは
CDN のキャッシュルール設定ミスにより
有料コンテンツが認証なしにアクセス可能になる、
または逆に有料ユーザーがコンテンツにアクセスできない障害が発生。
```

**CN 解決アプローチ**

```
① Signed URL / Signed Cookie の採用
   → CloudFront Signed URL で有料コンテンツを保護

② CDN の IaC 管理（Terraform / CloudFormation）
   → 設定をコードで管理し変更レビューを強制

③ CDN 設定変更の自動テスト
   → Canary リクエストで CDN 挙動を自動検証

参照:
  https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/private-content-signed-urls.html
```
